# Local simulated execution

`src/application/execution-service.ts` is called by the local stdio `execute_change` MCP tool. It operates only on the selected local SQLite database and invokes no cloud SDK, provider API, shell command, or network request. The stdio server owns and closes the configured connection. The tool accepts only a proposal ID and idempotency key; the actor comes from trusted server context, and reviewer approval comes from the authenticated CLI workflow.

`executeChange` requires an issued actor with `execute_change` before parsing input or touching the database. For a new request, one immediate SQLite transaction checks an independently recorded approval, current resource version, action eligibility, and current policy through execution preflight. The service appends a fixed audit attempt, applies the allowlisted fictional change with an expected-version write, checks the full persisted resource against the planned result, appends a success audit event, inserts one execution record, and moves the proposal from `approved` to `executed`. Any failure rolls all of those writes back. The transaction stores only synthetic IDs, fixed action and outcome values, a validated preview, and the success audit event ID; it does not store reasons, credentials, or raw errors in the execution result.

The execution table has a unique proposal ID and a unique executor-and-idempotency-key pair. An exact retry returns the original stored preview and audit event ID only when the issued executor, key, proposal, stored action, completed status, and approved decision remain consistent. It performs no new resource or audit write and does not apply today's policy to a historical completed result. A different key for the same proposal, reuse of a key for another proposal, or an altered stored action returns a conflict. Preflight is invoked only for a new execution, inside that same transaction.

The service records an attempt and success result in the successful transaction. A failed transaction does not leave behind its rolled-back attempt event. A failed-attempt audit record requires a deliberate append of a fixed safe outcome in a separate transaction after rollback. The MCP tool handler maps unexpected failures to a generic internal result.
