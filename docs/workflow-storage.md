# Workflow storage contract

`src/infra/sqlite/migrations/002_workflows.sql` stores proposed changes, independent reviewer decisions, and completed simulated executions. It contains no cloud operations or reviewer credentials. Application services must validate and bind every input through prepared statements; model-supplied identity or approval claims do not authorize a write.

## Proposals

A proposal references one resource, records its expected version, and holds a fixed allowlisted `action_type` (`resize_compute` or `disable_compute`) with object-shaped `requested_change_json`. `reason` and `approval_justification` are untrusted text. `policy_snapshot_json` is an object that later services must interpret using a versioned policy schema. The `request_fingerprint` is a lowercase hexadecimal SHA-256 digest of a fixed-order JSON tuple containing resource ID, expected version, action type, canonical requested-change JSON, and validated reason. Generated ID, timestamps, policy snapshot, actor ID, and idempotency key are excluded; the database reserves each `(proposer_actor_id, idempotency_key)` pair once. The repository returns the original row for an exact actor-scoped replay and rejects a different request under the same key. A replayed policy snapshot describes the original proposal; it cannot establish current eligibility or authorization.

The `status` column permits only `draft`, `pending_approval`, `approved`, `rejected`, `executed`, and `stale`. Repository transitions are `draft` to `pending_approval` or `stale`, `pending_approval` to `approved`, `rejected`, or `stale`, and `approved` to `executed` or `stale`; other statuses are terminal. The approval request is the only transition that sets `approval_justification`. Transitions to `approved` or `rejected` require a matching decision row, and a transition to `executed` requires an execution row. The database does not grant authority merely because a status says `approved` or a matching row exists. Services must transition from the expected prior status with an atomic compare-and-swap, recheck the resource version and current policy where required, and write associated audit events in the same transaction. The requested change remains immutable after creation.

## Decisions and executions

`approval_decisions` has at most one row per proposal and records a reviewer ID, `approved` or `rejected`, a reason, and a decision timestamp. The reviewer ID is not an authentication credential. `local_identities` is defined in migration 003; this decision table links to proposals. The local `proposals:list` and `proposals:review` commands authenticate a reviewer separately for each invocation. The queue display is read-only and advisory. The review service must require an authenticated, enabled reviewer, prevent the proposer from deciding their own proposal, and insert the decision and update status in one transaction after rechecking policy and the expected resource version. Approval requires a fresh eligible preview and an allowed current policy evaluation. Rejection still evaluates current policy, but a newly ineligible preview or denied policy must not prevent the reviewer from rejecting the pending proposal; rejection never authorizes execution.

`executions` has at most one row per proposal and stores the executor identity, execution idempotency key, object-shaped result, resulting resource version, and timestamp. It also requires an existing decision row for that proposal; the foreign key does not distinguish approval from rejection. Its unique `(executor_actor_id, idempotency_key)` pair reserves retries. Only a completed simulated change belongs in this table; a failed state transaction leaves no execution row or audit attempt. The result must contain only safe synthetic data, never credentials or internal errors. The execution service requires an approved decision, revalidates policy and resource state, updates only the targeted fictional resource once, inserts this row, marks the proposal executed, and appends audit data atomically. An exact authorized retry returns the original result; a conflicting key or payload fails.

`src/application/execution-service.ts` implements that composition. The local stdio `execute_change` MCP tool calls it with the trusted agent actor; HTTP does not expose it. It stores the validated original preview and success audit event ID for exact retries; `docs/execution-service.md` describes its transaction and replay boundaries. Authored competing-call cases are not evidence of simultaneous database writes.

All timestamps are UTC ISO 8601 strings supplied by application code. SQLite checks basic presence and proposal timestamp ordering, while services validate the format and transition order. JSON columns must be serialized from validated structured data and parsed and validated after reading. The schema bounds requested changes to 8,192 characters, policy snapshots to 65,536, and execution results to 16,384; application schemas should impose tighter limits where appropriate. The schema enforces foreign keys from proposals to resources, decisions to proposals, and executions to both proposals and decisions, but it cannot enforce actor permissions, policy outcomes, or legal transitions by itself.
