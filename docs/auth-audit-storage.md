# Local identity and audit storage

`src/infra/sqlite/migrations/003_auth_audit.sql` adds local CLI identities and application-written audit events. Neither table gives an MCP tool reviewer authority. Reviewer and auditor access must come from independently authenticated CLI sessions; an actor ID or role supplied in tool input is only untrusted text.

## Local identities

`local_identities` stores a lowercase ASCII username, a `reviewer` or `auditor` role, a disabled flag, and UTC ISO 8601 creation/update timestamps. Names are unique. There is no seeded account or plaintext password column. `password_salt` and `password_verifier` are binary values used with scrypt, and the row stores the bounded scrypt cost, block size, and parallelization used for that verifier. Enrollment generates a fresh random salt, derives the verifier from a masked interactive passphrase, and writes only the salt and derived bytes. `src/security/reviewer-auth.ts` checks role and disabled status, compares derived bytes in constant time, and re-reads the identity after asynchronous scrypt before issuing a CLI actor. Unavailable identities take a dummy scrypt path to reduce timing differences, though this does not guarantee constant total response time. Authentication allows at most three terminal attempts per invocation with a short delay and reports credential failures generically. The database checks storage shape; it does not authenticate a person. Authentication is per protected CLI command, not a persistent session or persistent rate limit.

## Audit events

`audit_events.sequence` is an explicit positive ordering key assigned by the application in a write transaction. Each event has a stable ID, actor type and ID, action, subject type and ID, object-shaped `event_json`, UTC ISO 8601 timestamp, preceding hash, and event hash. The first event has a null `previous_hash`; later events carry a lowercase 64-character SHA-256 hex digest. Subject and actor indexes support those filters; filtering by resource ID inside `event_json` scans the local audit rows. Agent, reviewer, auditor, and system actor types describe the source; the service must assign them from its trusted context, never from model text.

The event writer should encode `event_json` as compact canonical JSON with recursively sorted object keys. Compute `event_hash` as lowercase SHA-256 of the UTF-8 bytes of `JSON.stringify([id, actor_type, actor_id, action, subject_type, subject_id, event_json, occurred_at, previous_hash])`, using those values in exactly that order and the exact stored `event_json` text. In an immediate write transaction, read the current head, assign `sequence` as its sequence plus one (or one for the first event), set `previous_hash` to its `event_hash` (or null for the first event), then insert the new row with the computed hash. A verifier must read by `sequence`, detect gaps or bad predecessor links, and recompute every hash. No secret, passphrase verifier, bearer token, SQL, stack trace, internal path, or real customer identifier belongs in `event_json` or actor/subject text.

`src/infra/sqlite/audit-repository.ts` rejects non-JSON values, cycles, accessors, sparse arrays, excessive nesting, and oversized payloads before appending. This protects storage shape and bounded serialization; it does not redact a valid JSON string. `src/application/audit-service.ts` constructs closed payloads for proposal creation, approval requests, reviewer decisions, and execution attempts and results. It validates correlated fictional IDs, uses fixed outcome codes, and derives actor fields from an issued context. It never copies reason text, tags, passphrases, raw errors, or arbitrary caller objects into the payload.

Proposal creation, approval request, reviewer decision, and successful simulated execution append their events on the same SQLite connection and in the same immediate transaction as the state change. Exact proposal replay returns the existing draft without a second creation event. A failed execution result, if required, needs a separate deliberate transaction after the failed state transaction rolls back. The event writer does not itself authenticate a reviewer or authorize an execution.

Application code treats this table as append-only and writes an event in the same transaction as the corresponding state change. The schema checks required fields, JSON shape, hash format, and whether the first row has a predecessor; it cannot prove that a supplied hash is correct or prevent a database owner from editing rows. A person with file-level write access can rewrite SQLite and recompute the entire chain. This design provides limited tamper evidence for application paths, not external attestation or protection against that local attacker.

## Chain verification

`AuditListService.list` is a read-only trace query for authenticated reviewers or auditors. It bounds paging, accepts one proposal or fictional resource filter, and returns validated event metadata and resource IDs without raw `event_json`. Listing does not verify hashes; the separate verifier determines whether the stored rows currently form a consistent chain. Both read services recheck that the CLI identity is still enabled in their read transaction. The local `audit:list` and `audit:verify` commands authenticate a reader before calling them.

`AgentAuditService.getAuditLog` supports the local-only `get_audit_log` MCP tool. It requires the issued agent capability, bounds paging, and accepts at most one validated proposal or fictional resource filter. It reads only proposal workflow events and returns fixed summaries with safe synthetic metadata, excluding actor IDs, identity events, event payloads, and hashes. It is a trace view, not a chain-integrity result or a substitute for authenticated CLI audit inspection.

`AuditVerificationService.verify` accepts an issued actor with `verify_audit` and a caller-owned SQLite connection. It reads the chain in sequence order inside a read transaction and does not change records. The report contains `valid`, `totalEvents`, `verifiedEvents`, `firstInvalidSequence`, and `failure`. `verifiedEvents` counts the valid prefix; `firstInvalidSequence` is the expected sequence at the first failure. A deleted middle row is reported at the missing sequence. Failure codes distinguish invalid stored shape, noncanonical JSON, a sequence gap, a broken predecessor link, and a hash mismatch. An empty chain is valid with both counts zero. The report contains no event payload or other audit text.

Verification detects accidental or unsophisticated changes to the local chain. A removed tail, including the entire chain, leaves no gap and cannot be detected without a trusted external record of the former head. Someone who can edit the database file can rewrite all events and recompute all hashes. The report is not immutable external attestation, and `valid` means only that the stored rows currently form a consistent chain. The authenticated local audit CLI exposes this limited consistency report.
