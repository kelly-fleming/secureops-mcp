# Application workflow instructions

Follow root `AGENTS.md`, `docs/workflow-storage.md`, and `docs/auth-audit-storage.md` for proposal, review, and audit services. This file records the local composition rules for these services.

Use one configured SQLite connection for each workflow's repositories and audit writer. Wrap a successful state change and its audit append in the same immediate transaction so either both persist or both roll back. A failed attempt event, when required, needs a separate deliberate transaction after the failed state transaction has rolled back. An exact idempotent proposal replay returns the original draft without appending another creation event.

Build audit payloads from closed, application-owned fields: validated fictional resource and proposal IDs, fixed action and status values, policy version, and safe outcome codes. Derive the event actor from an issued context. Do not copy model input, proposal reasons, review text, tags, credentials, configuration, thrown messages, paths, or arbitrary objects into events. The audit repository validates storage shape and hash serialization; it does not make event content safe.

Proposal creation, approval requests, and reviewer decisions append their audit events in the same SQLite write transaction. The local MCP `propose_change` entry creates drafts only, and `request_approval` moves an eligible draft to pending review without deciding it. Proposal review is exposed only through the authenticated local CLI. An internal service or authored test is not evidence of a usable CLI or MCP feature. State which checks actually ran when reporting a change.

Approval request results may name the interactive `proposals:review` CLI command, run from the project root, with the validated proposal ID and an absolute-path placeholder for the same selected local database. Never include the configured database path or any credential in an MCP result; this instruction grants no reviewer authority.

Execution audit events use only validated proposal/resource IDs, current policy version, allowlisted action type, fixed outcome code, and an execution ID only for success. The local MCP `execute_change` entry calls the execution service with the issued agent actor; it cannot submit a reviewer decision. The service writes its success attempt and result with the resource update, execution row, and proposal transition in one immediate transaction. A failed outcome, if recorded, belongs in a deliberate transaction after the failed state transaction has rolled back; never include an exception message or untrusted idempotency key.

The audit verifier reads the caller-owned SQLite connection inside a read transaction. It checks canonical stored payloads, sequence continuity, predecessor links, and recomputed hashes, then returns fixed codes and counts without raw event text. Its `valid` result is a consistency check for present rows, not proof that no tail was removed or that a database-file owner did not rewrite the chain.

The audit list service is a separate read-only trace query. Require `inspect_audit` before parsing filters or touching SQLite, recheck the enabled reviewer or auditor identity inside the read transaction, bound paging, and return only validated metadata and fictional resource IDs. Never expose raw stored payloads or treat a listed row as proof that the chain is intact. The authenticated local audit CLI calls these read services; neither service grants approval or changes workflow state.

`AgentAuditService` is the narrower read-only service behind the local `get_audit_log` MCP tool. Require the issued agent's `get_audit_log` capability before parsing filters or reading SQLite. Bound paging, allow only one fictional proposal or resource filter, and return schema-checked workflow metadata with fixed summaries. Keep the SQL action allowlist tied to the fixed summary map, and bind every filter value. Exclude identity events, actor IDs, raw payloads, review text, credentials, and hashes. A trace listing is not chain verification and grants no reviewer authority.

Execution preflight is an internal check inside the execution service's immediate write transaction. It requires an issued `execute_change` actor, a coherent approved decision by an enabled independent reviewer, no prior execution, the exact current resource version, a fresh eligible preview, and allowed current policy. Its result is valid only for that transaction and does not itself authorize a later write or create an execution record.
Evaluate the current policy contents even when its version matches the proposal snapshot. The MCP execution boundary maps unexpected failures to a generic internal result. The execution service handles an exact authorized retry separately before invoking preflight for a new write.

An exact execution retry matches the issued executor, idempotency key, proposal, stored action, and completed decision before returning the saved preview and audit event ID. It performs no new resource or audit write and does not apply today's policy to the historical result. A new execution must compare the entire persisted resource with the planned allowlisted change plus one version increment before committing.

For a review of completed workflow work, inspect the changed service, its repository contract, and its caller route before changing adjacent services. Distinguish source implementation from an observed result. Fix concrete defects in the same trust boundary; do not reopen a completed task merely because its authored tests remain unrun.

When coverage work touches application services, add behavior-based cases for the missing trust or failure path before considering any narrow exclusion. The aggregate application threshold and authored concurrency or rollback cases are requirements, not evidence that a check passed. Record measured coverage only after an authorized runner executes it.
